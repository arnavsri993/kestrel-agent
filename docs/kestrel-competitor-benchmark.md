# Kestrel: documented competitors and measured switching hypotheses

Checked against primary documentation on **October 1, 2026**. This is a journey comparison and a proposed evaluation, not a performance ranking. Vendor statements below describe documented behavior; **standalone competitor trials: 0 for every product**. The Codex calls made through Kestrel count as Kestrel transport tests, not trials of the standalone Codex user experience.

## What Kestrel actually demonstrated

On four connected Codex accounts, one bounded live `gpt-6-astra` / `high` turn per account requested `workspace.read`; Kestrel's existing AgentLoop/runtime executed each scoped fixture read and recorded a **verified RuntimeToolExecution** containing the expected fixture marker. All four registrations reported effective Astra, read-only sandbox, and no sandbox network access; each outgoing turn retained the requested model and effort. These four runs intentionally stopped at a one-turn bound, before a final completion answer.

One additional isolated task on account 3 read `alpha.txt` (`ALPHA=12`) and `beta.txt` (`BETA=30`) through Kestrel, then returned exactly `TOTAL=42; inputs=alpha.txt,beta.txt`. Both reads were verified; the run and its persisted database state were `completed`. It used three Astra High turns within a four-turn cap. No paid fallback or production agent was created. Read-only tools deliberately do not generate mutation ActionReceipts; the verified records here are RuntimeToolExecutions.

Evidence: [four-account canaries](/private/tmp/kestrel-mission-runtime-current-canaries.json), [full completion canary](/private/tmp/kestrel-mission-runtime-completion-evidence.json), [current nonsecret account/quota status](/private/tmp/kestrel-mission-runtime-current-status.json). Source validation: 736 agent-core tests across 83 files and agent-core typecheck passed. These are tiny synthetic tasks: four account reads and one derived-answer completion, not reliability estimates. Automatic account failover, restart recovery, real connector work, local browser interaction, canonical installed-app delivery, long-running missions, and competitor superiority remain **unverified by this evidence**.

## Journey comparison

**Dots and Grok Bot compete for the same product promise: a persistent teammate that owns delegated work and follows through.** Both document ongoing context, cloud-computer work across tools, and returning results or requests for human decisions. Dots explicitly delegates to ChatGPT Work or Codex; Grok Bot documents parallel Bots and task handoffs. This shared journey is the relevant comparison for Kestrel: give it a real responsibility, change priorities while it works, return later, and inspect a finished result or a precise blocker. ## Three switching hypotheses to test next

These are proposed acceptance thresholds, not results or authorization to execute externally visible actions. Use existing product flows; no new architecture or agent template is needed. Judge Dots and Grok Bot on the same delegated responsibility and follow-through, with matched access and a clear finish line; feature descriptions alone cannot establish parity. Record account, model/effort, granted resources, tool trace, final artifact, elapsed time, interventions, and precise failure boundary for each journey. Competitor setup failures count separately from task failures.

1. **Browser-first completion saves the user a handoff.** On 10 matched journeys combining two authenticated read-only tabs and one granted local file, require at least 8 correct, source-linked final deliverables in the canonical Kestrel app, zero wrong-origin/account accesses, and at most one median intervention after setup. Then run the same journeys on Comet and one available Dots/Grok/Cowork surface; a switching claim requires at least 25% lower median interventions or elapsed time while matching completion quality. Current browser evidence: 0 journeys; competitor evidence: 0.
2. **Inspectable continuity makes recurring work worth trusting.** On 10 existing task restart/resume journeys and 10 scoped-memory checks, require at least 9 correct recoveries/recalls in each set, every returned fact traceable to its current source, and no cross-agent/private-profile disclosure. In 10 denied-scope or withdrawn-permission probes require 10 correct blocks and zero claimed actions without evidence. Compare with an available Hermes/OpenClaw persistent-work journey and an available Dots/Grok/Cowork journey before claiming an advantage. Current proof covers one persisted completed run, not restarts, recall, scheduling, or adversarial boundaries.
3. **Existing subscriptions remain usable without changing the user's deal.** Across 10 bounded quota/timeout/account-availability scenarios, require model, effort, tool catalog, and Kestrel authority preserved in every attempted route; complete at least 8 scenarios that have an eligible account. Require zero paid fallback and an explicit blocker for every scenario with no eligible account. Test route selection and failover separately from simple account access. Then compare setup and recovery friction against standalone Codex and the user's present workflow. Current proof is four successful account reads plus one full completion; automatic failover was tested synthetically, not observed live.

The supported claim today is narrow: **Kestrel can use four existing Codex accounts for actual Astra High tool requests, and can complete one simple scoped two-file task while keeping execution in Kestrel.** A leader, parity, production-readiness, or reason-to-switch claim needs the matched user journeys above.
